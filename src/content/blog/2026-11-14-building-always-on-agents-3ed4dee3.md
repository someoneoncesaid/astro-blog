过去几个月，常驻 Agent 再次受到关注。

常驻 Agent 能保留状态并主动行动。它们可以跨会话管理上下文，在没有人直接监督时采取行动。底层仍然运行和其他 Agent 相同的核心循环。区别在于外围架构，其中的基础组件决定了 Agent 何时醒来、哪些信息能跨次运行保留，以及工作结果如何送达用户。

这波回潮很大程度上得益于近期的模型进展，常驻 Agent 因而更切实可行。首先，新模型的判断力更强，能更可靠地理解用户意图，也更清楚何时该联系用户。其次，使用模型的成本在下降，长程任务获益尤其明显。举例来说，在一项长程编程基准测试中，Opus 5.5 每完成一项任务的成本比 Opus 5 低 78%，而在典型工作负载中，这一降幅为 40%。

客户开始问我们，怎样把这类体验集成进自己的产品。有些公司希望现有 Agent 更主动，有些则想从头构建常驻 Agent。

本文将拆解常驻 Agent 背后的基础组件，并说明它们如何配合。

## 常驻 Agent 的运行周期

「常驻」描述的是用户感受到的体验。实际运行中，Agent 大部分时间都在休眠，间歇醒来工作。

每一段工作称为一次运行（run）。Agent 接收事件，完成任务，然后保存本次运行的信息。运行在会话（session）内进行，会话保存消息和工具调用记录。运行结束后，Agent 回到休眠，周而复始。

![常驻 Agent 的运行时间线](/posts/2026-11-14-building-always-on-agents-3ed4dee3/assets/cc9d17c95d18.svg)

*图｜长时间的休眠穿插着短暂的运行。休眠期间不消耗 token。每次运行分四步：事件到达、启动会话、执行 Agent 循环、写回可跨次保留的状态。*

## 五个核心组件

常驻 Agent 的外围架构包含五个核心组件：事件收件箱、定时器、记忆、权限和发件箱。下面逐一说明。

### 事件收件箱

大多数 AI Agent 只在用户发消息时运行。常驻 Agent 可以由许多种事件触发，包括 Webhook、定时任务和后台作业。

一种容易想到的做法是让每个事件源直接调用 Agent，但这容易出问题。例如，两条事件同时到达，可能启动两次彼此竞争的运行。发生崩溃时，事件也可能就此丢失。

事件收件箱解决了这个问题。每个事件源把事件发到收件箱，由工作进程（worker）取出处理。

最简单的实现包含三个部分：

- 一份持久化的事件列表，通常是数据库表。
- 一个写入事件的处理器（handler），通常是 HTTP 端点。
- 一个读取事件的工作进程，通常是后台服务。

收件箱应跟踪每条事件的状态，并可依据事件源提供的唯一标识去重。关系型数据库很适合做收件箱，每条新事件追加为一行。我们建议先为每位用户设一个收件箱，需要提高并行度时再拆分。

![事件收件箱](/posts/2026-11-14-building-always-on-agents-3ed4dee3/assets/7b051a3d2c40.png)

*图｜HTTP 处理器把事件写入收件箱并唤醒工作进程。数据库表跟踪事件状态并去除重复事件。工作进程读取待处理事件，启动运行，等待结束后把事件标为完成。*

新事件到达时，处理器将它写入收件箱并唤醒工作进程。工作进程读取待处理的事件并启动一次运行。用户回复之类承接前序工作的事件会恢复已有会话，其余事件会开启新会话。

工作进程把事件交给 Agent 循环，等待运行结束，再把对应事件标为完成。实现时有几个细节值得注意：

- **尽快确认收到事件。** 有些来源（例如 Webhook 提供方）会把响应过慢视为失败。处理器可以做轻量校验。涉及提示注入等更深入的检查，应放到运行期间。
- **以收件箱为准。** 工作进程被唤醒后，应先到收件箱拉取最新的事件。如果它在运行中途退出，接替的工作进程仍能取到同一事件并重试。
- **同一收件箱同一时间只保留一个活跃的工作进程。** 这样可以避免两次运行重复工作或相互覆盖。运行中途收到新事件时，可以留给下次运行、并入当前运行，或中断后重新启动。
- **合批处理待办事件。** 比如用户连续发了几条消息，工作进程可以把它们合并到同一次运行中，Agent 只需回复一次。

### 定时器

定时器和事件收件箱配合，让常驻 Agent 能主动工作。定时器通常分为两类：一次性跟进和周期任务。一次性跟进由 Agent 自己设定时间，例如届时检查是否收到了回复。周期任务则按固定频率执行，例如每天发一期简报。

定时器应有独立的持久化存储，通常是另一张数据库表。收件箱只保存已经可以处理的事件。一次性跟进与周期任务可以使用相似的表结构，周期任务还需记录重复规则。

![定时器](/posts/2026-11-14-building-always-on-agents-3ed4dee3/assets/cf213749ce31.png)

*图｜一次运行将定时器写入数据库表，其中可以存放 Agent 设置的跟进事项，或用户安排的周期任务。调度器找出到期项，把事件写入收件箱，从而启动下一次运行。*

调度器通常作为后台服务，按固定间隔轮询存储，触发所有到期项。每次轮询时，它会：

1. 扫描存储，找出已到期的定时器。
2. 按类型更新定时器。一次性跟进标为完成，周期任务的到期时间更新为下一次执行时间。
3. 向收件箱写入事件并唤醒工作进程。

你可以自行实现调度服务，也可以使用支持持久化执行的引擎。

### 记忆

常驻 Agent 的工作分散在许多彼此间隔的运行中，依靠记忆维持连续性。

和收件箱、定时器一样，记忆也应有独立的存储。Claude Code 的自动记忆和 Messages API 的记忆工具使用文件目录来实现。对于常驻 Agent，这些目录应映射到持久化存储，通常是数据库或对象存储，这样工作进程退出后，记忆仍然存在。

一个经验法则是只在记忆中保存日后无法重新查到的信息。如果信息已经在工单系统等其他地方保存，记一个引用即可。常驻 Agent 应保存以下几类记忆：

- **用户指令。** 用户对 Agent 行为的要求应保存在单独的文件中，每次运行开始时加载。用户无法随时指导 Agent，因此这些指令需要跨次保留。
- **用户笔记。** 保存 Agent 对用户的了解，比如用户的角色、偏好和曾经提出的纠正。起初可以用一个文件，内容增多后再拆成若干小文件。拆分后，每次运行只加载索引，需要细节时再把相应文件读入上下文。
- **已发送的消息。** 记录已经告诉过用户的内容，避免重复。可以单独存一份文件，在每次运行开始时加载，也可以让工作进程加载最近几条发给用户的消息。
- **任务进度。** 每项进行中的任务都应有一份进度文件，记录已完成和待完成的事项。新的运行可以据此接续上次的工作。和用户笔记一样，每次运行开始时只加载索引，按需读取具体文件。

下面是一个目录组织示例。

![记忆目录示例](/posts/2026-11-14-building-always-on-agents-3ed4dee3/assets/4a6e6e67b0c0.png)

*图｜每次运行开始时加载 `instructions.md`、`index.md` 和 `reported.md`，按需读取 `notes/` 和 `progress/`。Agent 在运行期间写入记忆。*

以上讲的是运行期间如何保存记忆。还可以加入一种称为「做梦」（dreaming）的机制，通过回顾过去的会话整理记忆。「做梦」可以替换过时的条目，也能发现只有综合多次运行才能看出的问题或规律。我们关于 Agent 记忆的文章对此有更详细的介绍。

#### 上下文窗口里有什么

开始工作前，Agent 会加载系统提示词、工具定义和记忆文件。这部分初始上下文是每次运行的固定开销。我们建议精简这部分内容，并用提示词缓存降低成本。

新会话启动时，只带上这些初始上下文以及触发本次运行的事件。恢复已有会话时，还会带回该会话先前各次运行中的消息和工具调用。

如果会话过长，可以压缩早期消息，也可以开启新会话。两种做法都会损失细节，因此需要保留的信息应在工作过程中及时写入记忆。

![上下文用量变化](/posts/2026-11-14-building-always-on-agents-3ed4dee3/assets/fb9ac6e31a6c.svg)

*图｜系统提示词、工具和记忆在每次运行中占据一段固定空间。恢复已有会话时会带回完整记录，上下文随之增长，直到压缩将较早的内容转为摘要。*

### 权限

权限是常驻 Agent 风险最高的环节。运行期间，Agent 持有用户授权的访问权限，而且设计上是在无人值守时工作的。对于每一次工具调用，Agent 都需要判断是自行执行、拦截，还是等待批准。

常驻 Agent 使用的权限组件和其他 Agent 相同：

- **凭据存储。** 常驻 Agent 往往需要密码、访问令牌等敏感凭据才能做事。推荐使用位于 Agent 环境之外的代理。Agent 发出请求时不携带凭据，代理在转发前注入真实凭据。
- **自动模式。** 常驻 Agent 应能在无需用户持续输入的情况下工作。Claude Code 的自动模式已经解决了一部分问题。它使用分类器审查风险较高的操作，拦截被判定为危险的操作，让 Claude 寻找更安全的做法。最重要的决定仍需用户审核。
- **延后执行的工具调用。** 在 Claude Code 中，钩子可以挂起一次工具调用，等待用户提供额外信息。常驻 Agent 也可以采用这一模式，在采取某项行动前等用户澄清或批准。工具调用挂起后，本次运行结束，会话保存在调用中途。系统把请求展示给用户，例如用 MCP Apps 构建一张交互卡片。用户的答复作为事件进入收件箱，触发新一次运行。Agent 使用用户的输入恢复先前保存的会话。等待答复期间，工作进程还可以处理其他事件。

### 发件箱

大多数 AI Agent 会把响应边生成边传给用户。用户可以跟着看 Claude 如何分析问题、调用工具并写出答案。

常驻 Agent 的大部分工作发生在后台，用户通常收到的是结果和少量细节。

![发件箱](/posts/2026-11-14-building-always-on-agents-3ed4dee3/assets/67073ad7f373.png)

*图｜运行结束时可以安静收尾、调用发送工具，或通过挂起的工具调用向用户提问。待发消息保存到发件箱数据库表，由投递进程送达。待用户处理的请求既可以经过发件箱，也可以直接显示在产品界面中。*

一次运行可以有三种结局：

- Agent 向发件箱写入一条消息。
- Agent 判断无需发送消息。
- Agent 挂起工具调用，请求用户批准或补充信息。

多数常驻 Agent 用一个直接向用户投递消息的「发送」工具就够了。需要控制发送节奏，或让系统能从投递错误中恢复时，再使用独立的发件箱。

和事件收件箱类似，发件箱是专门保存待发消息的表。与工作进程相对应的是投递进程（dispatcher），通常也是后台服务。它读取待发消息，决定投递哪些内容，再送给用户。由挂起的工具调用产生的请求，可以经过发件箱投递，也可以直接显示在界面里。

除了把消息送到，还要调节发送频率。发得太多会打扰用户，发得太少又会漏掉用户需要知道的信息。我们建议建立评估来寻找平衡。实际使用中，可以先让 Agent 少打扰用户，再随着它逐渐产生价值，增加值得用户留意的通知。

## 五个组件如何协作

![五个核心组件的协作闭环](/posts/2026-11-14-building-always-on-agents-3ed4dee3/assets/52db0138d889.svg)

*图｜定时器与事件收件箱触发运行。运行在会话中使用记忆与权限。发件箱把消息送给用户，用户的回复再作为新事件进入收件箱。*

每次运行都始于收件箱中的一个事件，例如用户消息、Webhook 或定时器事件。工作进程取出事件，启动一次运行，在新会话或已有会话中唤醒 Agent。Agent 读取记忆，了解已有情况，在权限允许的范围内采取行动，再把新获得的信息更新到记忆中。运行完成后，Agent 可以向发件箱写入一条记录，再由投递进程把消息送给用户。

这些步骤形成了一个循环。一次运行可以设置定时器，在未来再次唤醒 Agent。用户回复消息时，答复作为事件回到收件箱。每次运行都很短，循环却能持续下去，这就是用户感到 Agent 一直在线的原因。

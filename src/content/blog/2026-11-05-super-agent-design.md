DeepSeek Harness 团队发表了《Super-agent 设计探索：迈向更自主的 Agent 系统》。这篇文章讨论的问题很具体：当模型已经越来越能独立完成一项工作，怎样让它同时推进多项工作、跨平台接续上下文，并且在长期运行中主动响应环境？

这也是我想把这篇文章展开讲一讲的原因。很多 Agent 演示已经能完成一次复杂任务，但放进日常工作，用户仍要切换会话、转述背景、追问进度。执行能力提高之后，协调工作的负担未必一起消失。

下面结合动图，沿着一个研发场景来看：群里有人反馈问题，Agent 开始排查，之后在 GitHub 收到评审与 CI 结果，最终把进展交付给用户。系统在这个过程中，需要怎样组织任务、消息与执行环境？

> 本文是对原文架构思路的解读。文中的 Super-agent 属于团队实践与原型探索，不是 DeepSeek 正式产品的功能发布；所有流程动画均为机制示意，播放速度不代表实际耗时。

## 01 任务越来越能自己做，为什么人还是很忙？

设想你同时推进三件事：修复一个缺陷、开发一项功能，再处理另一份 PR 的评审意见。

把这些工作全放进一个执行循环，背景确实集中，但长任务会占住处理过程，其他请求需要等待，多项任务的细节也容易混在一起。把它们分别放进独立会话，可以并行执行，但会话之间又不会天然知道彼此刚做过什么决定。

例如，你在群里决定采用方案 A，稍后在 PR 评论里改成方案 B。如果不同入口对应不同的独立上下文，谁来确认这是同一项任务，又由谁把最新决定送到正在执行的地方？在许多工作流中，答案仍然是用户自己。

![单会话与独立多会话的取舍](/posts/2026-11-05-super-agent-design/assets/65a2a82a31c5.gif)

*图 1：一个会话保留连续上下文，却容易串行排队；多个独立会话增加并发，也把跨任务协调和多处回复的问题暴露出来。这里对比的是两种简化设计，不泛指所有 Agent 产品。*

这也解释了为什么只增加 CLI、MCP 或外部消息连接器，还不足以解决问题。入口接通之后，仍需要决定消息属于哪个任务、后续由谁处理，以及本机休眠时系统如何继续运行。

## 02 Super-agent 想同时做到哪四件事？

原文给出的四个基础特征，可以对应到用户的四种感受。

- **连续**：无论在群聊还是 GitHub 提起同一个任务，它都能接上背景，理解最新决定，而不是要求用户从头复述。
- **高效**：正在推进的工作不会妨碍接收新指令，多项复杂任务可以并行、高质量地完成。
- **主动**：持续观察环境事件，判断哪些事项值得推进；无需介入时保持安静。
- **持久**：长期在线，接入真实工作环境，并在异常发生后恢复运行。

四项能力需要一起考虑。只有并行，没有全局连续性，容易出现各做各的；只有长期在线，没有事件判断，也不意味着系统会在合适的时机行动。

## 03 把协调与执行分开：Router＋Worker

文章提出的关键组织方式，是把“全局协调”与“具体执行”分到两个层级。

**Router 层**统一承接不同入口的人类交互，理解跨任务的高层关联，分派工作并汇总关键结果。它尽量不亲自执行具体任务，以免长时间的工具调用和细节推理占住交互入口。

**Worker 层**负责实际执行。不同 Worker 在隔离的上下文中专注于不同任务，并配备所需工具。复杂任务内部仍然可以使用子 Agent 或团队协作，这些内部细节不必暴露给 Router。

![双层架构、订阅直通与统一回复](/posts/2026-11-05-super-agent-design/assets/03cbfeef79a7.gif)

*图 2：新任务首先经过 Router 分派；Worker 隔离并行，后续相关事件可通过订阅直接送达。关键结论返回 Router，再由它统一面向用户回复。*

这里的双层是职责划分，不要求每层永远只有一个会话。原文选择了单个常驻 Router 会话作为直接实现，但也保留了未来分片或分层的可能性。

它与常见 Agent Team 的差异，主要在协调的范围。Team Lead 往往深入一个大任务的子步骤，频繁协调成员；这里的 Router 主要协调多项工作之间的关系，单项任务内部的拆解留给执行层。

从用户体验看，最值得注意的变化是：**用户不再需要把每个 Session 当成一个必须自己维护的工作单元。**底层可以有多个会话，前台仍然是一个能持续协作的 Agent。

## 04 事件来了，先判断要不要做，再判断交给谁

在持续在线的环境里，输入不只有人手动键入的提示词。群聊消息、代码评审、CI 结果、邮件和日程提醒，都可能成为驱动系统的事件，原文称之为 Trigger。

但能读到消息，不代表每条消息都值得调用模型。真实群聊里，大量内容只是闲聊、反馈或无需 Agent 介入的讨论。

文章采用两级过滤：确定性的程序规则先做准入判断，例如事件来源、群组范围和白名单；剩下需要理解语义的候选，再交给模型判断是否行动。

![程序与语义两级过滤](/posts/2026-11-05-super-agent-design/assets/8f93eb7fc392.gif)

*图 3：明确无关的消息可以先被规则挡住；通过规则的候选，仍可能被模型判断为不需要行动。过滤通过不等于已经授权执行。*

分派之后，还要处理同一事项持续产生的新消息。一个 PR、一个 IM 话题或一个邮件串下的相关事件，可以组织成一个 **Thread**。

当 Router 根据初始事件创建 Worker 后，Worker 可以订阅这个 Thread。之后的新评审、CI 结果等，由程序直接投递给订阅者，不必每次都让 Router 再调用工具转发。这样节省的是全局协调开销，而不是让 Router 失去全局可见性。

订阅也不是强制的一对一关系。同一个 Worker 可以订阅多个相关 Thread，同一个 Thread 也可以有多个订阅者。不过，收到相同通知只是提供了发现冲突的机会，并不能保证多个 Worker 修改同一环境时天然不会冲突。事件超出任务范围时，也需要交回 Router 重新分派。

## 05 有限的上下文里，放什么、留什么？

持续观察环境，会带来大量历史消息、任务进展与工具结果。全部塞进模型窗口，会挤占空间、稀释注意力；只给极少信息，又会让模型为了找背景反复调用工具。

原文用 **Inline & Spill** 描述这一取舍：近期很可能用到的信息直接内联进窗口，长内容和低频信息留在外部，在当前上下文保留摘要、ID 和读取入口。

![上下文内联与溢出](/posts/2026-11-05-super-agent-design/assets/370346504337.gif)

*图 4：先提供摘要与关联信息；长内容只展示开头，并保留续读入口。窗口之外的信息仍然存在，并没有被丢弃。信息注入量需要结合窗口预算和实际任务决定。*

例如，收到一条评审评论时，可以同时提供它所属 PR 的 ID、附近评论的摘要，以及负责该任务的 Worker ID。完整讨论不必一次注入，但下一步应该去哪里读，要让模型有迹可循。

这种做法进一步形成了“链式召回”：当前消息指向 Thread，Thread 指向 Worker，Worker 又关联另一个评审 Thread。每次读取都带出下一跳的引用，模型沿着关系逐层找回背景。

![沿引用逐跳召回旧任务](/posts/2026-11-05-super-agent-design/assets/f2a5ded325cb.gif)

*图 5：从一条消息出发，逐步读取相关对象。它展示的是按需检索路径，并不意味着长期记忆问题已经解决。*

原文也明确承认：当运行周期延伸到跨月甚至更久，长程记忆仍会成为扩展瓶颈。链式召回缓解了近期任务与会话历史的检索压力，但不能直接等同于无限、可靠的全局记忆。

## 06 主动推进，也要让人能随时插话

原文把一种提前行动的策略称为“投机执行”：在还不确定成果是否会被采用时，根据环境信号先在后台尝试，结果有价值再交付。

例如，群里有人反馈缺陷，Agent 可以先尝试复现、查找原因和形成修复方案；如果没有确认有效结果，就不必不断向群里发送过程消息。这一策略消耗额外后台算力，换取更少的人类等待与介入成本。

但主动执行不能让交互入口一直被占住。文章讨论的异步交互思路，是先返回工作已启动，后台继续运行，新消息仍可进入；任务结果准备好后，再作为新的事件送回。

![同步等待与异步交互](/posts/2026-11-05-super-agent-design/assets/d69d653968cb.gif)

*图 6：入口先确认任务启动，后台继续执行；新消息和随后返回的任务结果分别送达入口。任务的真实执行时间并没有因此凭空消失。*

交付还要适应渠道。IM 适合简短结论和直接问题，PR、邮件和文档适合完整背景、改动说明及验证结果。用户需要知道当前结果、待决策事项与不确定性，而不必在群里接收所有推理和工具调用。

后台尝试与对外操作也需要区分。能够提前起草、复现或准备方案，不意味着可以跳过当前环境对发送、提交、发布等动作的授权要求。

## 07 持久在线，需要拆开计算、状态与环境

本地 Agent 常把三个部分放在同一台机器：推进 Agent Loop 的计算、需要长期保存的会话状态，以及代码仓库和工具链等执行环境。设备休眠或离线，三者一起受到影响。

文章分两步解耦。先让推进循环的计算在云端运行，把会话等持久状态放进数据库；计算实例可以重启或替换，而任务连续性由持久存储提供基础。

随后，再把云端 Agent 与真实执行环境分开。代码、未提交修改、特定工具链和内网依赖可以留在原地，端侧的轻量 daemon 负责执行命令、返回结果。

![云端计算与本地执行环境分离](/posts/2026-11-05-super-agent-design/assets/4716311546a9.gif)

*图 7：Agent 在云端运行，执行环境留在用户机器。动图展示的是连接方式；私有凭据如何安全使用，仍需要额外机制保障。*

这样既可以接入用户自己的开发机，也可以连接托管机器或临时环境。但某项工作如果依赖当前离线的设备，仍要等待设备上线。云端持续在线，并不意味着所有执行环境随时可用。

更重要的是，状态持久化不自动等于任意外部动作都可以安全重放。故障发生时，哪些步骤已完成、哪些操作结果未知，仍然是恢复设计需要处理的具体问题。

## 08 Watchdog 看的是“有没有进展”，不只是“还活着吗”

长期运行的 Agent 可能进程正常、接口也能响应，却反复调用无效工具，或者持续偏离目标。这种问题不一定会触发传统的进程存活告警。

原文因此在主系统之外设置独立的 Watchdog Session，用定时消息驱动外部检查。它既关注接口报错和状态恢复失败，也判断 Worker 是否有实质进展、是否偏离整体目标，再决定怎样介入。

![Watchdog 发现停滞并介入](/posts/2026-11-05-super-agent-design/assets/bfb6cf923c25.gif)

*图 8：一条进度反复回摆，外部监督发现异常后介入。检测、修复和恢复推进是不同阶段；图中的进度不是实际测量百分比。*

这让监督从单纯的机器健康检查，进一步覆盖任务的推进情况。但 Watchdog 本身也是 Agent，需要自己的运行基础与权限约束，不能仅凭增加一个监督会话，就宣称系统已经具备无限可靠性。

## 09 实验支持了哪些判断？

原文使用约 300 条消息驱动不同方案，其中约 20 条是工作请求，其余包含闲聊、跟进、叫停和 CI 消息。各方案运行 5 次，编码工作由只消耗时间的工具代替。因此，实验主要衡量调度与协作，不能用来判断真实代码质量。

- **双层分工的完成时间更稳定。**实验中的 Super-agent，任务完成时间 p50 为 12.4 分钟、p95 为 15.7 分钟；中性提示下的“单会话＋Subagent 工具”，p95 达到 29.5 分钟。是否具备委派工具，与模型是否实际选择委派，是两件事。
- **订阅直通主要减少协调开销。**去掉直通后，任务完成时间基本相同，但 Router 决策次数增加约 30%，读缓存 token 从约 2323 万增至 3177 万，增加约 37%。这里统计的是读缓存 token，不是总费用，也不能据此推算统一的降本比例。
- **多会话本身也有代价。**维护多个会话会增加 token 消耗。这套架构在实验中以更多消耗换取更快、更稳定的完成，不能简单概括成“又快又省”。

Router 还可以把上一轮推理期间积压的事件合到下一轮处理。实验观察到，批次变大时单次请求耗时增长较慢，从而降低了每个决定分摊的推理时间。但这不意味着积压没有上限，也不意味着排队中的每一条消息都会更快得到响应。

## 10 真正值得关注的，是工作如何连续推进

这篇文章的价值，在于把多个容易混在一起的问题分别处理：用 Router 与 Worker 组织协作，用过滤与订阅路由事件，用引用组织上下文，用存储和执行环境解耦支撑长期运行，再用外部监督关注任务进展。

它也留下了明确的开放问题：更大规模下 Router 如何扩展，长期记忆怎样维护，用户如何中途接管，不同 Agent 实例如何在隔离上下文和权限的前提下协作，以及提示词注入、远程设备控制和凭据泄露如何防护。

尤其在云端 Agent 能够连接多台真实设备时，外部消息一旦影响了执行决策，其后果就不只是一段不正确的回复。能力、权限与信息隔离，需要和调度架构一起设计。

对我来说，这套思路提出了一个值得继续观察的问题：当我们越来越少亲自监督单项任务时，系统能否承担跨任务的协调，让人把注意力留给目标、关键选择与结果验收？

这次更新的主线只有一条：把 DeepSeek 服务端的内容拒答当成一类正常结果处理——错误码从 `MALFORMED_RESPONSE` 换成专用的 `CONTENT_REFUSED`，失败前先报已计费用量，并配了升级指南和回放快照。有意思的是这个功能在 40 分钟里走了三步：先加配置开关，再改成永远请求审查，最后把请求字段整个删掉，只留下拒答处理。另外两个 liveshare 提交，分别修桌面端隧道 worker 的启动和一个过期测试。

本稿证据来自 git 标签对比（`dsh-v0.2.2-rc.3` → `dsh-v0.2.2-rc.4`）与逐提交阅读；拒答流回放与 liveshare 桌面端行为本稿未实测。本地仓库的 master 停在 rc.3 合入提交（`39163dd`），rc.4 标签位于发布分支。

## 二、背景：refusal 曾被当作「响应格式错误」

DeepSeek 官方 API 在内容安全审查不通过时，会以 `stop_reason: "refusal"` 结束 Messages 流——[官方文档](https://api-docs.deepseek.com/guides/safety/#handle-refusals)把它列为调用方需要处理的一类终止原因。rc.3 的适配器 switch 只认 `end_turn` / `stop_sequence` / `tool_use` / `max_tokens`，`refusal` 落进 default 分支：

```
DeepSeek Messages stream: unsupported stop reason refusal  →  MALFORMED_RESPONSE
```

两个后果：

1. **语义错位**。提供方明确拒绝回答，用户看到的却是「响应格式错误」，排查方向被带偏。
2. **重试错配**。`MALFORMED_RESPONSE` 是重试策略的可选码（`retryChoice: true`），部署可以把它配成可重试；对一个注定再次被拒的请求重试，是白烧 token。

## 三、40 分钟的三步演进

三个 llm-deepseek 提交都在 2026-11-17 凌晨，00:23 → 00:34 → 01:04，前后 41 分钟。按序读完，正好把这个功能的设计取舍走了一遍。

**第一步（f250e232，00:23）：加开关。** 新增 volatile 配置 `safetyCheck`（默认 `false`）。开启时每个官方请求序列化 `safety_check: { level: 'high' }`，由提供方审查请求输入与模型输出；同时把 `refusal` 映射为新错误码 `CONTENT_REFUSED`，直接失败、不重试。

**第二步（15762ffc03，00:34）：改常开。** 删掉开关，所有官方请求一律带 `safety_check: { level: 'high' }`。并补上计费细节：拒答前已消耗的 token 是计费的，所以先 `yield` 一条 usage，再抛出 `CONTENT_REFUSED`。

**第三步（e68c033493，01:04）：删请求字段。** 把 `safety_check` 从请求序列化里整个去掉——这一步承认拒答并不需要客户端请求字段触发：没有请求安全审查时也会出现拒答。DSH 的职责是把这类拒答正确分类，而不是改请求行为。

净效果：`serialize.ts`、`config.ts`、`types.ts`、`wire-types.ts` 与 rc.3 逐字节相同，整个 llm 包的净差异只剩 `translate.ts` 的拒答分支和错误码目录里的一行 `CONTENT_REFUSED`。请求侧回到原点，响应侧多了一条正路。中间形态（开关、常开）从未出现在任何发布里。

## 四、rc.4 上的最终行为

- **分类**：`message_delta` 的 `stop_reason` 为 `refusal` 时，构造 `LlmError("DeepSeek refused to answer under its content safety review[: explanation]", 'CONTENT_REFUSED')`；提供方给出的说明（例如哪些图片被拦截）附在错误信息里。
- **计费**：`message_stop` 时先汇总 `usage`（输入 + 输出 + 缓存读 + 缓存写），`yield` 完 usage 再抛错。拒答消耗的 token 不丢账。
- **不重试**：`CONTENT_REFUSED` 在错误码目录里没有 `retryChoice`——它连重试策略的可选码都不是；`MALFORMED_RESPONSE` 保持可选不变。
- **下游表现**（README 的表述）：默认重试策略结束本次尝试；Web 撤回已流式显示的回复；Session 把它保存在 `assistant/attempt` 中，模型历史不含这段回复。流式输出前就被拒的输入仍以 HTTP 400 → `INVALID_REQUEST` 失败（与 rc.3 相同）。
- **回放快照**：`snapshots/session/deepseek-content-refusal/` 一份 authored NDJSON 展示完整形状——拒答前已流出一段草稿文本，`usage` 12/5/17，`finish` 与 `turn/end` 都是 `CONTENT_REFUSED` 错误。

## 六、liveshare：隧道 worker 以 Node 模式启动（#8634）

现象链条值得整段记下：owner 网关 worker 运行 `process.execPath`，Desktop shell 下它解析为 Electron 二进制；Electron 的 Node 模式由环境变量 `ELECTRON_RUN_AS_NODE` 决定，而 spawn 只转发了传输变量——于是 worker 作为**第二个 GUI 应用**启动，被 shell 的单实例锁以 exit code 0 结束，任何 worker 代码都没来得及跑。结果每个 share 都未注册，supervisor 不停启动替代品。

修复是把 Host 自己的 Node 模式随 spawn 转发（`workerNodeModeEnv()`，约 14 行，含测试重构）；纯 Node Host 没有该变量，环境不变。liveshare 仍是实验包，影响范围限于桌面端实验用户。

## 七、liveshare：过期测试修复（#8638）

spec 硬编码 live horizon `2026-11-14`，host 用 `Date.now()` 与它比较，从 2026-11-14 当天起必失败（[#8465](https://github.com/deepseek-ai/deepseek-harness/issues/8465)）。改为相对真实时钟：`PAST = now − 1 天`、`LIVE = now + 30 天`。只动测试文件，产品代码无变化。
